索引建得起来，只回答了设计问题的一部分。

本文从本站可读的迁移文件出发，推演字符串索引的设计问题，不是一次亲历的线上故障。遇到索引长度报错，把 255 改成 191 很快，但这个动作同时改了字段允许接收的数据，不能只以建表成功作为完成标准。

[![业务输入、字段与索引约束](/images/editorial/index-design.svg)](/images/editorial/index-design.svg)

*字段长度、索引预算与唯一性是三个需要分别核对的问题。*

## 先看仓库实际写了什么

基线迁移中，`articles.slug` 和 `tags.name` 都是 `varchar(255)`，并各自有唯一索引；用户迁移的邮箱也是 `varchar(255)`。订阅者迁移则把邮箱定义为 `varchar(191)`。这些字段使用 `utf8mb4_bin`，不能看到一个 191 就推断所有字符串列都有相同限制。

[![迁移字段对照](/images/editorial/mysql-schema.svg)](/images/editorial/mysql-schema.svg)

*这张图对应迁移源文件的定义，不代替运行中数据库的结构检查。*

还有一个容易忽略的地方：Ent 的 Article Schema 注释提到默认 `VARCHAR(191)`，但手写基线迁移明确是 255。注释表达的预期与 SQL 已经不同。本文据此能确认的是源文件存在差异，不能断言线上表采用哪一个值；确认运行结构仍须查看目标数据库。

## 字符数不是索引字节数

`VARCHAR(n)` 的 n 表达字符容量，索引长度限制需要按字节理解。以 utf8mb4 的最大编码宽度估算，191 个字符对应最多 764 字节，255 个字符对应最多 1020 字节。这解释了为什么同样的字符长度，在不同字符集下可能碰到不同的索引边界。

但计算出 1020，并不能直接宣布索引非法。InnoDB 的限制还受页大小、行格式与数据库版本等条件影响；联合索引还要算其他列。191 常见于兼容旧限制的设计，不能脱离环境变成今天所有字段都要遵守的业务上限。

面对假设中的错误，检查顺序可以很短：先记录准确报错和目标版本，再看表的字符集、排序规则、行格式与完整索引定义。下面是隔离验证时可用的只读检查示例，表名应换成被研究的对象：

```sql
SELECT VERSION();
SHOW CREATE TABLE articles;
SHOW INDEX FROM articles;
SHOW VARIABLES LIKE 'innodb_page_size';
SHOW VARIABLES LIKE 'sql_mode';
```

把准确 DDL 放入匹配目标条件的隔离环境重现，比在开发机随意创建一个同名字段更有解释力。开发库能建表，并不能消除目标环境配置差异。

## 三种改法改变了不同东西

| 方案 | 保留什么 | 必须承担的代价 |
| --- | --- | --- |
| 缩短字段 | 在新长度内做完整值比较 | 原来合法的长输入可能被拒绝 |
| 使用前缀索引 | 原字段的存储容量 | 索引只覆盖部分字符串 |
| 调整索引或键设计 | 可按业务重新定义身份 | 消费者和查询路径需要重新核对 |

例如业务允许两个长标识符拥有相同的前 191 个字符，只在后缀不同。完整唯一索引本应允许两者共存；若改成唯一前缀索引，第二个值可能被判冲突。若先截断再存储，两者甚至会变成相同数据。它们都不是原来唯一性语义的等价替换。

排序规则也是契约的一部分。应用是否把邮箱转小写、是否允许大小写不同的标签，不能仅由字段长度回答。测试要覆盖业务实际使用的归一化路径，再检查数据库比较行为，而不是从 `_bin` 名称推导所有输入的处理结果。

## 让验证覆盖写入与读取

推演验证至少准备边界长度以内、恰好达到边界、超过边界三组数据，并包含中文或四字节字符；记录 SQL mode，确认超长输入会得到预期结果，不能依赖未检查的截断行为。唯一性再使用相同值、大小写变体以及相同长前缀的不同值。

假设最终决定把字段缩短，还要检查历史数据长度、接口校验、表单限制与导入脚本。表单拒绝了超长输入，不等于其他写入入口也拒绝。迁移回退只能恢复结构，不能自动找回已截断的数据，这也是优先在副本上验证的原因。

这些检查也应留下输入与预期，而不只是迁移执行成功的日志。后续有人调整字段或字符集时，才知道原先保护的业务行为是什么。

对本站而言，255 与 191 的并存提供了一个检查起点。真正需要决定的是每个字段代表什么、接受哪些输入、依靠什么保证唯一，而不是把某个数字统一到全仓库。
