关系声明、数据库中的关联行与接口返回，需要用同一组数据对照。

本文用文章与标签做一个可复现的案例推演。设定是文章能查到标签，标签方向却查不到预期文章；这不是本站真实事故记录。先固定数据，再沿声明、存储、查询三层检查，比看到空列表就修改 ORM 关系更有效。

[![文章与标签的案例关系图](/images/editorial/ent-relations.svg)](/images/editorial/ent-relations.svg)

*两篇文章共享一个标签，用来区分实体是否存在与关联是否存在。*

## 先把关系说清楚

[![Ent 官方文档中的用户、宠物与群组关系图](/images/editorial/ent-official-relations.png)](/images/editorial/ent-official-relations.png)

*图片来自 [Ent 官方 Edges 文档](https://entgo.io/docs/schema-edges/)，Apache-2.0。官方图使用用户、宠物与群组，下面换成文章与标签。*

案例里创建文章 A、B，以及标签 Go、数据库。A 关联两个标签，B 只关联 Go。预期不是模糊的“关联正常”，而是 A 查到两个标签，Go 查到 A、B，数据库标签只查到 A。任何一条不成立，都有明确的输入和预期可供追踪。

本站 Schema 的声明可以作为对照：

```go
// Article.Edges
edge.To("tags", Tag.Type)

// Tag.Edges
edge.From("articles", Article.Type).Ref("tags")
```

`Ref("tags")` 指向 Article 侧的边名，不是 SQL 表名，也不是 Tag 侧方法名。两侧都没有用 `Unique()` 限制成单个关联。阅读时要把边名、目标实体和反向引用一起看，不能只确认存在两个相似的字符串。

## 数据库里存的是关系行

仓库基线迁移中的 `article_tags` 有 `article_id`、`tag_id` 两列，以两列组合作为主键，并分别引用文章和标签。组合主键约束同一对关系重复出现，却允许一篇文章对应多个标签，也允许一个标签对应多篇文章。

可以用下面这张预期表手工核对测试夹具：

| article_id | tag_id |
| --- | --- |
| A | Go |
| A | 数据库 |
| B | Go |

如果反向查询为空，先判断这三行是否真的写入，再看查询条件。生成代码能编译，只能证明应用代码的类型关系成立，不能证明目标数据库已经应用对应迁移。尤其共享开发环境里，Schema 文件、迁移文件与实际表结构可能处在不同时间点。

迁移中的外键带有 `ON DELETE CASCADE`，它针对物理删除后的关系清理。本站文章状态还包含软删除：更新状态不会触发物理删除外键动作。因此“删除后还查得到”也可能是生命周期过滤问题，不能立即归因于关系方向。

## 空结果可能只是没有加载

假设文章详情查到了 A，却看到返回对象里的标签集合为空，还需要区分“没有预加载”与“数据库没有关系”。本站数据层读取文章时使用 `WithTags()`；脱离这条读取路径自行写测试，不能默认普通实体查询会自动填充所有边。

推演中可以分别从实体发起边查询，再与预加载结果比较：

```go
// 示意：a 与 goTag 是夹具中已创建的实体。
tags, err := a.QueryTags().All(ctx)
articles, err := goTag.QueryArticles().All(ctx)
```

若边查询正确而接口结果为空，检查转换时是否带出标签；若裸查询正确、加筛选后为空，检查文章状态与过滤参数。把查询、加载、转换逐段拆开，才能避免用修改 Schema 去修复展示层遗漏。

## 解除关联要保住共享实体

再从 A 移除 Go，预期只剩 A—数据库与 B—Go 两条关系，Go 标签实体仍存在。若直接删除 Go 实体，B 的关联也会消失；这与编辑 A 的标签不是同一操作。

本站更新路径使用 `ClearTags()` 再添加本次标签，表达的是替换当前文章的标签集合。它值得验证的边界包括空集合、保留一个标签，以及共享标签仍被其他文章引用。删除闲置标签属于另一项业务规则，不应藏在解除关联里。

测试夹具最好给每个实体分配固定且易读的标识，断言标签 ID 与文章 ID，而不是只比较数量。两个错误标签也能凑出数量二，只有集合比较才能发现错连。测试结束后再重新查询，不复用内存里已经加载的边，避免把旧快照误当成数据库当前状态。

如果改动涉及关系声明，应先查看生成迁移的差异，确认是否会新建中间表或搬移外键。已有数据如何保留，是迁移设计的问题；单靠重新生成客户端，并不能把旧关联自动变成新结构。

最小回归可以按“建立三条关系—验证双向集合—移除一条—重新读取”执行。比较集合而非返回顺序，并额外断言 Go 实体与 B—Go 仍在。这样的测试能指出破坏发生在哪一步，也给未来调整 ORM 或迁移留下具体的行为约束。
