陶瓷、箱包与工艺品设计中的 AI 需求，往往同时涉及对话、图像生成和多步骤工作流。设计人员需要在一个产品里完成这些操作，后端则要将不同模型、绘图节点、任务状态与计费规则接起来。这是我在爱格创参与的 AIGC 聚合与调度中台的业务背景。

我承担后端核心研发与部署上线，前端由同事负责。技术栈以 Python、Django / DRF 为主，配合 Channels、Asyncio、Celery、Redis、MySQL、Docker 与 Nginx。平台聚合 GPT-4o、Midjourney、Stable Diffusion 和 ComfyUI，围绕流式对话、工作流绘图和商业化使用组织能力。

## 流式对话：处理被拆开的 Markdown 图片链接

对话输出采用 SSE 持续传输，结果里包含 Markdown 图片链接。一个完整链接可能被分在不同的数据片段中，网络到达的边界与 Markdown 语法的边界并不一致。直接将每段内容交给页面解析，会让尚未闭合的链接进入渲染过程，出现展示错乱。

我实现了基于状态机的 SSE 缓冲层，让输出先经过语法片段的状态处理，再交给前端。这里的关键是在连续文本输出与图片链接完整性之间安排缓冲：需要保留尚未完成的片段，并在后续数据到达后继续识别，使包含图片的回答能够稳定展示。

## 用 Function Calling 组织工具与推理过程

平台中的任务还涉及工具调用与多步处理。我基于 Function Calling 开发轻量 Agent 调度器，支持工具调用、ReAct 推理链，以及短期和长期记忆；Redis 与向量库用于相应的记忆存储。

这一层将模型返回的调用意图接到实际工具执行，再把工具结果放回任务过程。它连接了对话、工具和记忆，使一次用户需求可以在多个步骤之间推进。对于行业设计工作流，调度器承担的是将模型能力组织成连续业务过程的工作。

## 模型网关：应对外部 API 抖动

平台同时使用多个模型服务，外部供应商的可用性与调用限制会直接影响用户任务。我实现了多供应商故障转移、Token 限流与请求去重，通过 Redis 滑动窗口支持调用控制，并在第三方 API 抖动时切换备用线路。

网关把供应商接入与业务入口连接起来，处理的是调用链中的稳定性问题。故障转移、限流和去重各有职责：故障转移处理服务线路异常，限流控制调用节奏，去重约束重复请求。它们共同支撑上层的对话和生成任务。

## 绘图任务与 GPU 节点调度

ComfyUI 工作流需要实际的 GPU 节点承接任务。绘图过程比普通接口请求更长，也会受到显存状态和节点可用性的影响。我使用 Celery 优先级队列组织任务，配合心跳探活判断节点状态，并在任务执行前处理 VRAM 回收，降低显存不足引起的失败。

这部分工作的对象同时包括等待中的任务和正在运行的节点。任务进入队列后要选择可用资源，节点状态需要持续更新，任务执行前还要为显存使用做好准备。将排队、节点探活与显存处理串起来，才能让工作流绘图成为平台可持续提供的能力。

## 支付、订阅与按量计费

生成能力进入商业产品后，需要与支付和使用权益衔接。我独立完成微信支付 V3 与支付宝的全流程接入，处理 RSA / AES 回调验签，并参与订阅制、按量计费与会员权益体系的实现。

这里的交付范围从支付渠道接入延伸到产品的使用规则：用户购买什么权益、生成任务如何计费、订阅与按量使用如何共存，都属于平台后端需要承接的业务。支付与生成模块放在同一产品里，形成了从使用能力到付费的完整路径。

## 运营观察与上线维护

我还使用 Pandas 与 ECharts 建设运营数据大屏，围绕日活、付费转化与算力消耗组织分析，并接入钉钉机器人进行故障报警。运行中的问题由此可以从业务使用和资源消耗两个角度观察。

这段项目经历覆盖了 AI 应用后端的多个层面：流式输出需要照顾页面渲染，Agent 调度需要连接工具和记忆，绘图工作流需要管理算力，商业化则需要支付与权益体系。我主要负责将这些能力落实为平台后端，并完成部署上线与后续维护。
