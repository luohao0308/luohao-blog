代码写完、测试通过，到远端合并之间还隔着一次具体的权限判断。我在 [dev-workflow](https://github.com/luohao0308/dev-workflow) 里实现交付守卫，是想把“可以继续”拆成能够核对的条件：谁执行、操作哪一版代码、平台证据是否仍然有效。否则一句“检查都过了”，可能混在一起指本地测试、上一轮 CI 和当前 PR。

## 三类条件各自负责什么

流程要求决定变更是否需要 Issue、PR 和 CI；权限决定谁能 push、创建或更新 PR、合并；质量门决定当前版本是否满足要求。它们需要分别成立。例如，修复已经完成且 CI 通过，但策略中的执行者仍是用户，AI 的工作就应停在准备命令和证据。

`core/scripts/delivery_guard.py` 会先读取 manifest 的策略。`actor=user` 会直接拒绝 AI 执行；`actor=ai` 也不是拿到一张长期通行证，仍要提供绑定具体操作的一次性授权。`auto` 省掉授权范围内的重复交互，不省略授权检查。修改长期权限又是另一件事，不能从当前权限反推自己有权扩大它。

## 把一句授权拆成可比较的字段

假设准备把 `fix/article-filter` 合入 `main`，光记录分支名不够。分支会移动，同名 remote 的地址也可能改变。守卫把仓库路径、remote 名称和 URL、操作、源与目标引用、完整 SHA、过期时间和最大次数放在一起核对。

下面是便于阅读的范围示意，不是可直接执行的授权文件：

```text
operation   merge
source      fix/article-filter
target      main
sha         <完整提交对象 ID>
expiresAt   <本次授权的到期时间>
maxUses     1
```

如果随后补了一次提交，分支名虽然没变，SHA 已经不同。旧授权和旧检查结果都不能平移到新版本。代码还会比较本地源分支实际指向的提交与请求中的 SHA，避免请求写着一个版本，实际准备交付另一个版本。

## 平台证据必须回答当前问题

本地有提交，不代表远端已经收到；本地检查通过，也不能代表平台 required checks 已满足。因此不同操作需要不同证据。PR 创建或更新前要核对远端源分支版本，合并则要核对 PR 编号、开放状态、head/base、准确 head SHA、required checks 和是否可合并。

这能解释一个常见的时序问题：读取 PR 时检查通过，之后有人又推了提交。如果执行端仍拿旧证据合并，检查覆盖的对象已经变了。流程要求提供五分钟内且绑定对象的托管平台证据，紧邻操作再核对；证据新鲜仍不等于永远有效，最终平台操作也应约束预期版本。

守卫本身读取并校验传入证据，不是远端分支保护服务。采集端是否可信、实际命令是否遵守检查结果，仍是执行链必须承担的责任。不能因为一个 JSON 写着 `requiredChecksPassed: true`，就把它当作平台已经独立证明的事实。

## 预检与消耗之间的取舍

检查时可能只是准备交付，不能每看一次条件就扣掉授权次数；真正操作之前，又不能无限复用同一授权。守卫用 `--consume` 区分这两步，并把消耗写入本地账本。正式操作前的最终检查负责记录次数，普通预检用于发现字段、版本或权限问题。

这个顺序偏向保守：检查已消耗授权，后续操作失败，也不能把失败解释为可以自动重试。结果未知时更要先确认平台状态，而不是重新执行。网络超时不等于远端没有完成动作，盲目重试会让次数限制失去意义。

还有一类检查容易漏掉：同一份证据被换到另一个 remote 或目标分支使用。即使 SHA 相同，操作对象也已经变化，字段绑定必须逐项比较，不能只校验提交号。

本地账本也有边界。它记录本机流程，不是跨机器的集中授权服务；多个执行入口要遵守同一权限约束，仍需要可信宿主和托管平台能力配合。

## 验证重点放在拒绝路径

检查这种守卫时，我更关心只改变一个条件会发生什么。可以用临时仓库和构造证据，分别覆盖执行者为用户、SHA 不匹配、授权过期、次数用尽、PR 已关闭、目标分支错误、required checks 未通过等情况。每个用例都应明确在哪一步拒绝，而不只是断言最终退出失败。

还应区分两种测试：字段校验通过，证明守卫接受这一组输入；真实平台操作成功，才证明执行链连通。前者不能替代后者，更不能推出部署健康。这样划分证据，才能在后续扩展时知道究竟补了哪一层能力。

## 守卫之外仍然需要平台边界

本地规则适合让 AI 在操作前停下来核对，但它无法约束绕过脚本的其他客户端。受保护分支、平台审批与代码审查承担更外层的约束。发布、迁移和部署也各有对象及恢复条件，不能由“允许合并 PR”顺带授权。

我保留这套分层，是因为它让失败能够被具体描述：是权限不对、版本变了，还是检查缺失。处理方式随之不同，也比让 AI 再说一次“我确认过了”更容易复核。
