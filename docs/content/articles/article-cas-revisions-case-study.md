同一篇文章开了两个编辑窗口，一个改标题，一个补正文。两个窗口都显示“保存成功”时，后一次保存可能已经把前一次修改覆盖了。

本文从[这个博客](/projects/luohao-blog)的实现中抽出一个设计案例。场景中的窗口名、正文和版本号用于说明并发条件；代码、接口与测试入口对应仓库中的实际实现。

## 先固定两个窗口看到的内容

假设文章当前是版本 7，窗口 A、B 都在此时打开。A 将标题改成“请求重试”，B 在旧标题下补了一段正文。两边本地输入都有效，问题出在它们共同依赖了同一份旧数据。

| 时刻 | 窗口 A | 窗口 B | 服务端状态 |
|---|---|---|---|
| 打开编辑页 | 读取版本 7 | 读取版本 7 | 版本 7 |
| 本地修改 | 修改标题 | 补充正文 | 版本 7 |
| A 保存成功 | 取得版本 8 | 仍持有版本 7 | A 的内容，版本 8 |
| B 提交旧基准 | 保留已保存结果 | 携带 expected_version=7 | 拒绝冲突写入 |

这里希望保护的是已经提交的结果，同时保留 B 的输入。B 可以对照最新版本重新整理；服务端不能替作者猜测两份正文该怎样合并。

## 保存前再读一次，仍然可能同时通过

一种直观做法是在保存入口查数据库，比较当前版本与请求版本，相同才继续更新。若“查询”和“更新”分成两个步骤，A、B 仍可能同时读到 7，并各自通过比较，随后先后执行无条件更新。

事务也需要配合具体的写入条件。仅仅把几条语句包进事务，不能证明旧窗口的请求会被拒绝。必须确认最终负责认领版本的数据库语句仍带有客户端的基准条件。

本站要求更新请求提交 expected_version。service 会读取当前文章、合并允许修改的字段，但传入业务层的版本依然取自请求。若在这一步把请求版本替换成刚读到的最新值，旧窗口就能悄悄获得新的写入资格，冲突保护也失去意义。

## 用一次标量 UPDATE 认领版本

下面是认领动作的示意 SQL。命名参数用于表达绑定位置，省略了实际驱动绑定与完整保存事务：

```sql
UPDATE articles
SET version = version + 1
WHERE id = :id
  AND version = :expected_version
  AND status <> :deleted_status;
```

判断依据是影响行数：恰好更新一行，才继续写正文；影响零行，返回版本冲突。缺少版本条件的请求则在进入保存链路前被拒绝。

实际代码使用 Ent。这里有一个值得单独检查的细节：带标签、分类等关联的更新可能先选出 ID，再执行后续写入。只看 builder 上出现了 Where，还不足以确认版本条件留在了实际更新语句中。因此实现先执行仅涉及版本的标量条件更新，取得行锁；成功后，再通过同一个事务客户端保存内容与关联。

在正常成功提交路径中，A 先认领版本 7 并推进到 8。B 使用同样的旧版本条件继续写入时，无法再认领这一行。若 A 在后续步骤失败并回滚，版本递增也会一起撤回，不会留下一个已经宣布成功的半成品。

## 修订快照跟随正文一起提交

防覆盖保护当前内容，修订历史则保留成功写入之间的变化。两者需要落在同一个提交边界里，否则可能出现正文已经改变、对应快照却没有保存的情况。

本站的保存事务依次完成版本认领、正文及标签分类更新、修订保存；需要生成公众号同步任务时，outbox 也在这个数据库事务中入队。关联校验、快照写入或入队失败，都不能只提交其中一部分。

对于接入修订功能之前已有的文章，首次变更会先补一份旧版本 baseline，再记录新版本。基线只能表示当时保留下来的那份内容，作者未知时也不补造身份。历史页不能据此声称掌握了功能接入前的每次编辑。

Elasticsearch 同步在数据库提交之后尝试执行。搜索失败不会把已保存正文改报成保存失败，避免作者因此重复提交。这个分界可以继续看[正文保存成功后的搜索同步恢复](/posts/article-search-sync-case-study)。

## 409 之后，编辑器先保住输入

版本冲突会返回 HTTP 409。后台显示“文章已有新版本，修改与本地草稿已保留”，保留当前表单和对应本地草稿，不自动刷新页面，也不自动使用新版本号重发。

编辑器除了提示冲突，还要记住草稿基于哪个版本，并区分账号、文章与窗口。否则，恢复旧草稿后若直接套用最新版本号，仍可能覆盖其他窗口的工作。

成功保存也只清理对应提交的原稿。等待响应期间继续输入的新内容，需要继续留在编辑器中。作者整理冲突、阅读最新版本，再基于新版本发起一次明确保存，才是下一次写入。

## 恢复历史，是产生一个新版本

假设当前已到版本 11，作者希望恢复版本 7 的内容。恢复请求同时指定“取哪个历史快照”和“当前基准是 11”。服务端读取自己保存的快照白名单，沿保存事务生成版本 12，旧的 7、11 都继续保留。

恢复复制标题、摘要、Markdown、标签分类、封面和精选等内容字段，保持当前 ID、slug、发布状态、首次发布时间与阅读点赞计数。已发布文章恢复后，公开正文会随新版本更新；保留的是当前发布状态与首次发布时间，不改链接，也不倒退统计。

历史资源也需要重新检查。分类按照原 ID 与 slug 核对，后来同名重建的分类不能被当作原对象；历史封面不可用时返回明确错误。恢复期间又有其他窗口写入，也必须遵守当前版本条件，不能覆盖新提交。

## 怎样验证这条链路

在仓库根目录、具备项目要求的 Go 工具链时，可以先运行不连接数据库的 service 回归：

```sh
go -C backend test ./internal/service \
  -run '^(TestArticleVersionRequired|TestUpdateUsesSubmittedVersion)$' \
  -count=1 -v
```

这两项检查缺少版本会被拒绝，以及 service 确实传递请求基准版本。它们不能代替真实数据库并发验证。

真实 MySQL 场景由 TestArticleCASMySQL 验证两个并发旧版本请求仅一项成功、一项冲突，并检查失败事务没有留下标签残片；TestArticleHistoryMySQL、TestArticleRestoreMySQL 继续覆盖快照和恢复。它们只在配置 BLOG_REVISION_MYSQL_DSN 后运行，需要任务自有、可销毁的隔离数据库及测试要求的迁移和基线数据。默认跳过不算验证通过，不能将这些测试指向生产或共享数据库。

本文的短 SQL 先用内存 SQLite 检查了一次命中、一次失配。随后在独立 MySQL 8.4 样例中，从迁移 16 和旧文章基线升级到 19，运行上述三项及两项分类并发回归，五项均通过且没有跳过。它验证的是隔离数据库中的锁、事务和恢复边界，不是线上压测。

仓库根目录可以复现这组隔离验证：

```sh
python3 scripts/test_article_revisions.py
```

脚本拒绝远端 Docker endpoint，并核对自己创建的容器标签与回环映射；只创建并清理该容器与匿名卷，使用 127.0.0.1:13327，不读取生产配置。运行前需有 Docker、Python 3 和项目要求的 Go 工具链，并确认该端口可用。完整浏览器复现前置条件见仓库的 [E2E 说明](https://github.com/luohao0308/luohao-blog/blob/400d24244ae607a5a22bf7565166f811c1b558fa/scripts/e2e/README.md)。
