我整理岗位时，同一家公司经常会在不同渠道出现。把链接收进表格容易，第二天回头看，难的是分清这个岗位值不值得继续看、已经做了什么、下一步应该在什么时候做。我做的[机会工作台](/projects/job-application-workbench)，就是围绕这三个问题组织页面和数据。

## 从岗位记录里分出自己的判断

我把公开岗位和个人进度分成两层。岗位条目记录名称、来源和地区。同一个机会可以关联多个来源，打开详情时还能回看原链接。个人层保存匹配理由、优先级和后续动作。岗位来源变了，可以重新看判断依据。已经发生的投递和面试仍有各自的记录。

用一条虚构岗位走一遍。示例公司 A 的产品设计实习出现在优先投递页。先看来源与个人匹配信息，再决定是否开始投递。列表同时显示近期行动，回到工作台时可以继续处理之前留下的事项。

## 投递开始后，页面关心的是下一步

开始投递后，记录进入投递进程。这个页面需要回答「现在在哪一步」「接下来做什么」，所以把阶段和跟进动作放在同一条记录上。安排面试时可以附上时间与轮次，面试后再补问题、可改进的地方与下一步。

如果把这些都塞回岗位条目，更新一个动作就容易改掉岗位本身的信息。分别建模之后，同一个岗位链接可以保留原样，跟进动作可以改期，面试也能单独复盘。

## Vue、FastAPI 和后台进程各负责什么

Vue/Vite 负责工作台和交互，页面通过同源 API 查询列表、展开详情和提交动作。FastAPI 处理认证、校验和业务写入，PostgreSQL 保存岗位、匹配记录、投递和面试。个人数据按当前账户限定查询范围。直接打开某条机会链接时，页面可以请求单条详情，无需把整份岗位列表拉回浏览器。

有些操作需要更多时间，例如重新计算匹配或生成导出文件。API 接受请求后登记任务，由独立的 Python Runner 处理，界面再读取任务状态。这样，用户能看到旧匹配结果与新一轮刷新进度之间的区别。导出也是同样的交互，先看到已排队，完成后才出现可下载的文件。

## 怎样验证这条路径

浏览器测试使用同一组虚构岗位和投递记录，覆盖从查看岗位到跟进投递的关键交互。它可以验证筛选请求、状态提示和页面反馈。这里的两张图用相同方式复现。后端权限、数据库约束和后台任务另有各自的验证边界。

这个项目最实用的设计是让每个页面回答一个具体问题。岗位页帮助决定下一步做什么，投递页帮助继续已经开始的事，面试复盘保留之后还能用到的经验。
